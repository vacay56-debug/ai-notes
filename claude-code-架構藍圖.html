CLAUDE.md + SKILLS + HOOKS + SUBAGENTS + PLUGINS

這是一套讓 Claude Code 從「單次問答工具」進化為「可長期維運之工作系統」的架構。 七個元件各司其職、彼此分層——如同一份建築剖面圖：從最底層恆常生效的核心規則， 逐層向上擴充知識、安全機制、任務委派，最終打包成可供整個科室安裝使用的套件。 本頁在原始資訊圖的基礎上，補充機制細節、實際範例與行政文書工作的應用情境。

00 / 導論

為什麼需要「架構」，而不只是「提示詞」？

許多人使用 Claude 的方式，是每次開新對話就重新交代一次規則、重新貼上範例文件、重新解釋一次業務背景。 這種做法在偶爾使用時沒有問題，但一旦進入每天都要處理公文、預算書、簡報、採購文件的常態工作， 重複交代規則本身就會變成一種成本。

智能體開發套件（Agent Development Kit）的核心精神，是把「規則要交代幾次」與「規則有多重要、多需要被強制遵守」 拆成不同的層級來管理：有些事情永遠生效（CLAUDE.md）、有些事情按需喚起（Skills）、 有些事情必須被程式鎖死而非依賴 AI 自律（Hooks）、有些事情最好交給獨立分身處理（Subagents）， 最後再把整套設定打包分享出去（Plugins）。

這七層彼此不是互相取代的關係，而是解決不同問題的工具—— 官方文件將其歸納為：CLAUDE.md 處理「恆常情境」、Skills 處理「隨需知識與流程」、 MCP 處理「外部連接」、Subagents 與 Agent Teams 處理「隔離」、Hooks 處理「自動化」、Plugins 處理「打包分享」。

建議導入順序
  • 先建立 CLAUDE.md，定義最基本、不常變動的規則（語言、格式、禁止事項）
  • 發現自己重複交代同一套「流程」時，把它收進 Skill
  • 發現某條規則「AI 有時會忘記遵守」時，改用 Hook 鎖死
  • 發現某項任務「查證過程很長、但只需要看結論」時，交給 Subagent
  • 整套設定穩定之後，打包成 Plugin 供同仁安裝
01–05 / 核心分層

五層核心架構

LV.01

CLAUDE.md — 記憶層

THE MEMORY LAYER
永遠載入、永遠生效——智能體的「憲法」

CLAUDE.md 是一份純文字規則文件，Claude Code 每次啟動都會自動讀入，不需要每次重新說明。 角色類似機關內部的「作業要點」：不是拿來查閱的參考資料，而是每次執行任務都必須遵守的基本規範。 多層 CLAUDE.md 是疊加生效的：所有層級同時貢獻內容，指示衝突時，較具體的規則通常優先。

架構規則 Architecture rules 命名慣例 Naming conventions 測試期望 Test expectations 專案地圖 Repo map 代理人指引 Agent guidelines
  • 全域 Global ~/.claude/CLAUDE.md ——適用這台電腦上所有工作，例如固定使用繁體中文、慣用語氣
  • 專案 Project .claude/CLAUDE.md ——只適用於特定資料夾，例如某次法規研修案的專屬術語與格式
範例：救護業務科文書規則片段
# CLAUDE.md — 緊急救護科文書工作規則

## 語言與格式
- 一律使用繁體中文（教育部標準字體、臺灣慣用語）
- 英文專業術語首次出現：中文（英文全稱，英文縮寫）
- 公文一律採三段式：主旨／說明／辦法（或擬辦）

## 檔案組織
- 簽稿存放於 /公文/簽/
- 預算文件依年度存放於 /預算/{年度}/

## 禁止事項
- 未經確認，不得逕行變更正式發文字號
- 不得於文件中臆測未經證實之統計數據
要點提醒
保持精簡。CLAUDE.md 不是用來塞入完整法規全文或大量參考資料的地方——那是 Skills 的工作。 內容塞得越多，每次對話消耗的上下文就越多，反而可能讓 Claude 抓不到重點。
LV.02

Skills — 技能層

THE KNOWLEDGE LAYER
隨需載入的模組化知識包，不常駐上下文

若 CLAUDE.md 是「憲法」，Skill 就是「業務手冊櫃」——平常收在櫃子裡， 只有遇到對應業務時才被取出參考，用完即釋放，不會一直佔用主線的思考空間。 現行版本的 Skills 已整合了原本的自訂指令（Slash Commands）： 一個 Skill 既可以被 Claude 依情境自動喚起，也可以用 /技能名稱 手動呼叫。

描述比對 Description matching → 自動觸發 Auto-invoked → 任務專屬情境 Task-specific context
  • 結構 Structure 每個 Skill 是一個資料夾：SKILL.md（何時啟用、如何操作）+ 參考文件／腳本／範本／範例
  • 關鍵 Key 可於獨立子代理中執行——即使參考資料龐大，也不會拖垮主線對話的上下文空間
對照你目前的設定
你在 Claude 中已經配置了對應救災救護組不同業務的 Skills：公文起草、預算說明書、政策簡報、 採購文件、EMS 國際政策研究、出國考察報告——這正是「技能層」在實務上的樣子： 每個 Skill 只在對應情境被喚起，彼此互不干擾，也不會平白佔用其他業務的上下文空間。
LV.03

Hooks — 掛鉤層

THE GUARDRAIL LAYER
確定性規則，不是 AI 判斷——如同 Git 的 hooks 機制

Hooks 是寫死的自動化規則，在特定事件發生時強制執行，不經過、也不受 AI 自行判斷是否遵守。 這一點對公部門工作特別關鍵：某些「絕對不可以」的紅線，可以用程式規則鎖死， 而不是只靠提示詞去「拜託」AI 遵守——測試顯示，僅在 CLAUDE.md 寫「禁止執行某危險指令」， 遵守率約七成；改用 Hook 攔截後，可達到百分之百強制封鎖。

事件觸發 Event fires → 比對條件 Matcher checks → 執行指令 Command runs
PreToolUse 動作執行前 PostToolUse 動作執行後 SessionStart 工作階段開始 Stop 任務結束 SubagentStop 子代理結束
  • 類型 Types command（指令）、http、mcp_tool、prompt、agent 五種掛鉤類型
  • 硬性攔截 Hard block PreToolUse 掛鉤回傳 exit code 2，即可在動作執行前直接擋下，無法被繞過
情境應用
例如：寫入檔案時自動排版、封鎖危險指令（如 rm -rf）、任務完成時發送通知—— 延伸到文書工作，也可以設定「覆寫正式簽核文件前，先自動備份一份存檔」，避免正在處理的公文草稿被意外覆蓋。
LV.04

Subagents — 子代理層

THE DELEGATION LAYER
委派專職任務給獨立上下文視窗，讓主線保持乾淨

可以想像成把一項專門工作外包給科內的專責承辦人——你只交代任務、只收結果， 不需要知道對方過程中查了多少資料、改了多少次。子代理擁有自己的上下文視窗、工具與權限， 過程中的雜訊不會回流到主線對話。

委派 Delegate only ← 結果 Results only
  • 單向 One-way 子代理不能再委派給其他子代理，避免無限遞迴、失控增生
  • 與 Agent Teams 的差異 Subagent 為單向回報；Agent Teams 則是多個獨立行程之間可雙向溝通、平行協作
  • 範例 Examples 程式碼審查員（Code Reviewer）、測試執行員（Test Runner）、探索員（Explorer）——各自擁有獨立上下文、工具與權限
延伸思考（非既有功能，示範同一邏輯的應用方式）
同樣的委派邏輯，理論上也能延伸到行政工作：例如設定一個專職比對法規異動的子代理， 或是專職檢查公文格式是否符合三段式規範的子代理。重點在於——把「過程很長、但只需要看結論」的工作， 交給獨立子代理處理，而不是塞滿主線對話。
LV.05

Plugins — 外掛層

THE DISTRIBUTION LAYER
打包 skills / agents / hooks / commands，如同 npm 套件之於軟體開發

前四層通常是個人或單一專案在使用；外掛層則是把整套規則、技能、掛鉤與指令包裝成單一單位， 讓同仁可以一鍵安裝，不必每個人重新設定一次。外掛中的 Skill 會自動加上命名空間 （例如 /公文起草外掛:簽稿），避免與個人本機設定的技能同名衝突。

skills/ agents/ hooks/ commands/
  • 散布方式 Distribution Marketplace（市集）／ Team install（團隊安裝）
  • 適用時機 When 需要在多個資料夾重複使用相同設定，或要分享給科內、跨科同仁時

08 / 橫向規範

貫穿所有層級的共同規範

如同建築法規不專屬於哪一層樓、卻適用於整棟建築，以下五項規範不隸屬於任何單一層級，而是所有層級都必須共同遵守的底線。

01

安全與權限

Security & Permissions —— 每一層的動作都需經過權限檢查，尤其涉及檔案寫入與外部連接時。

02

可觀測性與日誌

Observability & Logging —— 記錄每次工具呼叫與子代理行為，便於事後稽核與除錯。

03

錯誤處理與重試

Error Handling & Retries —— 任務失敗時如何重試、如何回報，而不是靜默中斷。

04

成本與權杖管理

Cost & Token Management —— 每加入一項功能都會消耗上下文，過多反而降低準確度。

05

測試與評估

Testing & Evaluation —— 規則與技能是否真的達到預期效果，需要持續驗證，而非設定完就不管。

10 / 常見誤解釐清

三個關鍵提問

Q ── Hooks 是不是 AI 自己決定要不要執行？

不是。Hooks 是寫死的確定性規則，事件一觸發就執行，不涉及 AI 臨場判斷。這也是它能用來守住「絕對不可以」紅線的原因——一般指示的遵守率約七成，Hook 攔截則接近百分之百。

Q ── Subagent 可以再委派給另一個 Subagent 嗎？

不行。系統刻意限制子代理不能再產生子代理，只能單向委派、單向回報結果，避免無限遞迴、失控增生。

Q ── Skills 會不會一直佔用上下文，拖慢對話？

不會。Skill 的內容平常「收在櫃子裡」，只有被判斷相關時才載入，且可在獨立子代理中執行，用完即釋放，不會持續佔用主線的上下文空間。
