LLM Engineering Framework · 三層架構對照

提示工程VS脈絡工程VS束具工程

與大型語言模型（Large Language Model, LLM）協作的三個工程層次：從「寫好一則訊息」、「管好一段記憶」，到「建好一部機器」。層次越高，人的角色越像系統設計師而非對話者。

01

提示工程

Prompt Engineering 訊息層 · The Message

聚焦於單一輸入的品質：把角色、背景、指令、範例與輸出格式組裝成一則完整提示（Prompt），送入模型推論後取得回應。若結果不理想，回頭調整最弱的那個成分再送一次。

Pipeline · 運作流程
1組裝 Compose將五大成分組合為一則提示
2送出 Send提交至 LLM 進行推論
3生成 Generate模型產出回應
4精修 Refine調整最弱成分，重新送出

工作單位：一則輸入（one input）。每次互動是獨立事件，優化對象是「這一則訊息寫得夠不夠好」。

五大組成成分

成分內容作用
角色
Role		「你是一位資深□□專家……」設定模型的專業視角與語氣基準
背景
Context		相關文件、對話歷史、任務背景提供判斷所需的事實基礎
指令
Instructions		具體要做什麼、步驟為何界定任務範圍與執行順序
範例
Examples		少樣本示例（few-shot pairs）用輸入→輸出對示範期望品質
格式
Format		JSON 結構、表格、三段式架構等約束輸出形態，利於後續使用
實務範例公文起草提示
# 一則完整提示，五大成分齊備 ↓

【角色】你是內政部消防署救災救護組的資深承辦人，
熟悉《文書處理手冊》與三段式公文格式。

【背景】本科擬函請各直轄市、縣（市）消防局於 8 月底前
回報 115 年度救護技術員（EMT）複訓需求人數，
作為明年度訓練量能規劃依據。

【指令】請起草一份「函」稿：
1. 主旨一句話，以「請 查照」結尾
2. 說明分項敘述法源依據與回報方式
3. 語氣公務、精簡，避免贅詞

【範例】主旨寫法參考：
「為辦理○○事宜，請於○月○日前惠復，請 查照。」

【格式】依「主旨／說明／辦法」三段式輸出，
說明段落逐項編號（一、二、三）。
觀察重點：五個成分各司其職。若產出的主旨太冗長，只需精修「範例」成分（多給一個好主旨示範）即可，不必重寫整則提示——這就是「調整最弱成分」的精神。
02

脈絡工程

Context Engineering 記憶層 · The Memory

聚焦於脈絡視窗（Context Window）這塊有限預算的管理：多輪互動中，資訊來源眾多（查詢、系統提示、檢索文件、工具輸出、記憶、先前對話），必須由「策展者（Curator）」篩選、壓縮、捨棄，決定每一步「什麼留在視窗內」。

Pipeline · 運作流程
1蒐集 Gather彙整六類資訊來源
2策展 Curate篩選／壓縮／捨棄，塞入有限視窗
3餵入 Feed視窗內容送入 LLM 推論
4更新 Update新輸出成為下一步的脈絡

工作單位：每一步「留在視窗內的內容」（what stays in the window, step by step）。優化對象不是單則訊息，而是資訊的取捨策略。

六類資訊來源與策展策略

來源特性常見策展手法
使用者查詢
User query		當下任務的核心訊號永遠保留，優先權最高
系統提示
System prompt		固定行為規範精簡化，避免佔用過多預算
檢索文件
Retrieved docs		量大且雜訊多僅取相關段落，摘要後餵入
工具輸出
Tool outputs		結構化但可能冗長擷取關鍵欄位，捨棄原始雜訊
記憶
Memory		跨對話的長期資訊只載入與當前任務相關者
先前對話
Prior turns		隨輪次線性膨脹壓縮為摘要，早期輪次可捨棄
實務範例法規研修知識庫的脈絡策展
# 任務：比對《緊急醫療救護法》第 20 條各縣市收費規定
# 視窗預算有限，策展者的取捨決策 ↓

[保留・原文] 使用者查詢：「彙整六都救護車收費差異」
[保留・原文] 《緊急醫療救護法》第 20 條條文全文
[壓縮・摘要] 22 份縣市自治條例
              → 壓縮成一張「縣市×收費級距」對照表
[壓縮・摘要] 前 15 輪討論
              → 濃縮為 3 行結論：「已確認法源、
              已排除離島特例、待補台中市修正版本」
[捨棄]       檢索到的 8 篇新聞報導全文
              （僅留 1 行：輿情關注收費爭議）
[捨棄]       與本題無關的 EMT 訓練討論串

# 結果：視窗只裝「回答本題必需的最小資訊集」
# 下一輪：本輪產出的對照表 → 成為新的脈絡
觀察重點：同樣的提示技巧，若視窗被 8 篇新聞全文塞爆，模型反而抓不到重點。脈絡工程的價值在於「捨棄什麼」與「保留什麼」同等重要——這正是 Claude 專案（Projects）知識庫、檢索增強生成（Retrieval-Augmented Generation, RAG）系統設計的核心課題。
03

束具工程

Harness Engineering 機器層 · The Machine

聚焦於整部自動化系統的設計：把脈絡工程（蒐集區）與提示工程（組裝區）包進一個可循環的束具（Harness）中，讓模型能行動（呼叫工具、調度子代理人）並被驗證（Verify）。驗證未通過即帶著更新後的脈絡重跑，直到產出可信的最終結果。

Pipeline · 運作流程（Gather → Act → Verify 循環）
1蒐集 Gather策展者整理脈絡，塞入視窗（脈絡工程區）
2組裝 Compose視窗內容組成提示（提示工程區）
3行動 ActLLM 呼叫工具、調度子代理人專家
4驗證 Verify測試／LLM 評審把關；未過→重跑循環

工作單位：整個「蒐集→行動→驗證」的循環（the loop）。優化對象是系統的可靠度，而非任何單次輸出。

關鍵組件

組件角色對應實例
策展者
Curator		入口守門：篩選、壓縮、捨棄脈絡RAG 檢索器、記憶管理模組
工具輸出

子代理人

驗證器

重試機制

實務範例採購文件自動審查束具
# 目標：招標規格書產出後「自動審查、自動修正」
# 一個完整的 Gather → Act → Verify 循環 ↓

① Gather  策展者載入：使用者需求
           + 《政府採購法》相關條文摘要
           + 歷年同類案規格書範本（壓縮版）

② Compose 組裝提示：「依上述法規與範本，
           產出○○器材財物採購規格書草案」

③ Act     LLM 產出草案，並呼叫工具：
           · 子代理人 A（法規審查員）：逐條核對
             有無違反《政府採購法》第 26 條
             （規格綁標禁止）
           · 子代理人 B（格式審查員）：檢查章節
             編號、必要欄位完整性

④ Verify  Python 驗證腳本執行：
           ✓ 必備章節齊全？
           ✗ 發現「指定廠牌未加註『或同等品』」
           → 驗證未過

⑤ Retry   將驗證器的錯誤訊息加入脈絡，
           重跑 ①～④ → 第二輪通過 ✓
           → 輸出最終規格書給使用者
觀察重點：人不再逐字審稿，而是設計「審稿的機器」。附帶驗證腳本的 Claude 技能（Skills）、Claude Code 的測試迴圈、n8n 自動化流程，本質上都是束具工程的產物——品質由系統保證，而非單次提示的運氣。

三層框架總對照

三者非互斥，而是包含關係：束具工程之內有脈絡工程區與提示工程區。

面向 提示工程 脈絡工程 束具工程
隱喻訊息（The Message）記憶（The Memory）機器（The Machine）
工作單位一則輸入每步留在視窗內的內容整個蒐集→行動→驗證循環
核心問題這則訊息寫得夠好嗎？有限視窗該裝什麼？系統能自我把關嗎？
優化手段調整角色／指令／範例／格式篩選、壓縮、捨棄資訊來源設計工具、子代理人、驗證器與重試
典型失敗模式指令模糊、缺範例、格式失控視窗塞爆、關鍵資訊被雜訊淹沒缺驗證器導致錯誤輸出直達使用者
代表場景單次對話、一次性任務長對話、知識庫、RAG 系統Claude Code、代理人工作流、n8n 自動化
人的角色寫作者圖書館員／策展人系統架構師
When · 何時用
單次任務 → 提示工程

起草一份公文、翻譯一段文件、產出一張表格。把五大成分寫齊，就能拿到穩定品質。

When · 何時用
長期協作 → 脈絡工程

經營專案知識庫、跨多輪修訂大型文件。決定「留什麼、丟什麼」比「怎麼問」更關鍵。

When · 何時用
批量自動化 → 束具工程

需要無人值守、可重複、可驗證的產線。把審查標準寫進驗證器，讓循環替你把關品質。
