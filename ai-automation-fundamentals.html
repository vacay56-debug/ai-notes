AI 自動化系統基礎架構 FUNDAMENTALS OF AI AUTOMATION SYSTEMS

一套可靠的人工智慧（Artificial Intelligence, AI）自動化系統由九個層面組成：從工作流的啟動方式、決策邏輯、系統整合，到資料、監控、擴展、安全、成本與對齊控制。點選左側堆疊圖跳轉章節，點開任一概念卡即可展開「範例教學」，每則教學均含情境與可直接套用的實作範例。

SYSTEM STACK
L1 智慧工作流 L2 AI 決策層 L3 整合層 L4 資料與知識 L5 可觀測性 L6 擴展性 L7 安全與治理 L8 效能與成本 L9 控制與對齊
L1

智慧工作流

Intelligent Workflows

定義自動化「何時啟動、如何推進、何時交回人工」的骨架。

觸發式啟動 Trigger-Based範例教學
由事件啟動流程：API 呼叫、Webhook、使用者操作。
情境

信箱收到帶有「電子報」標籤的郵件時，自動摘要並寫入知識庫。

實作（n8n 流程） 
# 節點串接順序
Gmail Trigger (label = 電子報)
  → HTTP Request：呼叫 LLM API 產生 300 字摘要
  → Google Drive：附加至「每日摘要.md」

重點：觸發器（Trigger）只負責「偵測事件」，後續處理交給下游節點，二者解耦後流程才容易維護。

事件串流 Event Streaming範例教學
對持續產生的資料流做即時決策，而非批次等待。
情境

勤務派遣系統每分鐘產生數十筆紀錄，需即時偵測「同區域十分鐘內超過三件」的壅塞訊號。

實作（概念流程） 
派遣紀錄 → 訊息佇列（如 Kafka / MQTT）
        → 串流處理：滑動視窗 10 分鐘計數
        → 超過門檻 → 推播告警至值勤群組

重點：串流處理的核心是「視窗」（window）——在時間窗內聚合、比對門檻，事件過了視窗即丟棄，記憶體佔用固定。

目標導向代理 Goal-Driven Agents範例教學
給定目標，由 AI 自行規劃並執行多個步驟。
情境

只下達一個目標：「彙整三份會議逐字稿，產出決議事項追蹤表」。

實作（代理自主拆解） 
# 代理內部規劃（自動產生）
1. 讀取三份逐字稿檔案
2. 逐份抽取「決議」與「待辦」句
3. 合併去重，標註負責單位與期限
4. 輸出 Excel 追蹤表

重點：代理（Agent）與一般提示的差別在於「規劃—執行—檢查」迴圈；下指令時給目標與驗收標準，不必列步驟。

人機協作把關 Human-in-the-Loop, HITL範例教學
低信心或高風險任務自動升級為人工處理。
情境

公文自動分文：AI 判斷承辦科別，信心不足時轉人工分文。

實作（判斷邏輯） 
if confidence >= 0.90: 自動分文並記錄
elif confidence >= 0.70: 分文 + 標記「請複核」
else: 進人工待辦佇列，附 AI 建議與理由

重點：設兩道門檻而非一道——高信心全自動、中信心「先做後審」、低信心「先審後做」，兼顧效率與風險。

L2

AI 決策層

AI Decision Layer

依任務性質選用不同決策引擎：能寫死的用規則，需預測的用模型，需理解語意的才用 LLM。

規則引擎 Rule Engine範例教學
確定性邏輯與護欄，結果可預測、可稽核。
情境

採購案依金額自動判定適用程序，這類法定門檻絕不該交給 LLM「推理」。

實作 
if 金額 >= 公告金額: 公開招標
elif 金額 >= 逾公告金額十分之一: 公開取得書面報價
else: 得採小額採購

重點：法規門檻、金額級距、格式檢核一律用規則引擎；LLM 輸出也應再過一層規則檢核（護欄），確保合規。

機器學習模型 Machine Learning Models, ML範例教學
從歷史資料學習規律，做預測分析與評分。
情境

依過去三年勤務量、節慶與天候，預測下月各分隊救護出勤量，作為排班參考。

實作（Python 概念） 
from sklearn.ensemble import GradientBoostingRegressor
X = 特徵[["月份","連假天數","均溫","前月出勤"]]
model.fit(X_train, y_train)
預測 = model.predict(下月特徵)

重點：ML 適合「數字進、數字出」的預測；資料品質（欄位一致、無缺漏）比演算法選擇更影響成敗。

大型語言模型推理 LLM Reasoning範例教學
具語境理解能力的語言智慧，處理非結構化文字。
情境

來函文字千變萬化，規則寫不完——用 LLM 判讀要旨並輸出結構化結果。

實作（提示設計） 
你是公文分類助手。閱讀以下來函，僅輸出 JSON：
{ "類別": 訓練/採購/法規/國際交流,
  "要旨": 30 字內, "時限": 有/無 }

重點：讓 LLM 輸出固定格式（JSON），下游程式才接得住；「僅輸出 JSON、不加說明」要寫進提示。

多代理系統 Multi-Agent Systems範例教學
規劃者、執行者、審核者分工協作。
情境

文件審查：一個角色起草，多個角色以不同立場審查，再由整合者定稿。

實作（角色分工） 
規劃者 Planner：拆解審查面向（法制/預算/執行）
執行者 Executor：逐面向產出審查意見
審核者 Verifier：檢查意見有無矛盾、遺漏
整合者：彙整為單一修正建議表

重點：多代理的價值在「立場分離」——審核者不知道執行者的思路，才審得出盲點；單一模型分次扮演即可實現。

L3

整合層

Integration Layer

讓 AI 與既有系統互通：新系統走 API，即時通知走 Webhook，老系統靠 RPA。

API 與 gRPC APIs & gRPC範例教學
結構化的服務間通訊，系統整合的標準做法。
情境

自建工具需要呼叫 LLM 服務產生摘要。

實作（HTTP API 呼叫） 
const res = await fetch("https://api.example.com/v1/messages", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ messages: [{ role: "user", content: 全文 }] })
});

重點：REST API 通用性最高；gRPC 用於高頻、低延遲的內部服務通訊。行政應用九成情境 REST 即足夠。

Webhooks即時推播觸發範例教學
事件發生時由來源系統「主動推送」，免輪詢。
情境

GitHub 儲存庫收到推送（push）時，自動重新部署靜態網站。

實作 
# GitHub Repo → Settings → Webhooks
Payload URL: https://自動化平台/webhook/deploy
Content type: application/json
Events: push
# 平台收到後執行：建置 → 發布 GitHub Pages

重點：Webhook 與 API 方向相反——API 是「我去問」，Webhook 是「它來報」。定時輪詢改 Webhook，延遲從分鐘降到秒級。

工具呼叫 Tool Calling範例教學
LLM 依需求自行呼叫外部工具（查詢、計算、寫檔）。
情境

問 AI「下週三下午有沒有空」，它需要真的查行事曆而非猜測。

實作（工具定義） 
tools: [{
  name: "query_calendar",
  description: "查詢指定日期區間的行程",
  input_schema: { start: "date", end: "date" }
}]
# 模型回傳 tool_use → 程式執行查詢 → 結果回填 → 模型作答

重點：工具的 description 寫得越具體，模型選用越準；工具呼叫是「模型出題、程式執行、結果回填」三步迴圈。

RPA 自動化 Robotic Process Automation, RPA範例教學
模擬人工操作舊系統介面，適用於無 API 的老系統。
情境

老舊內部系統只有網頁介面、沒有 API，需每日登入下載報表。

實作（瀏覽器自動化） 
# Playwright（Python）
page.goto(內部系統網址)
page.fill("#account", 帳號); page.fill("#pwd", 密碼)
page.click("text=每日統計")
page.click("text=匯出 Excel")

重點：RPA 是「過渡方案」——介面一改版就壞，務必加上失敗告警；能爭取到 API 就淘汰 RPA。

L4

資料與知識

Data & Knowledge

AI 回答的品質上限由資料決定：先汲取、再清洗、建索引，最後讓回答「有憑有據」。

資料汲取 Ingestion範例教學
批次與串流兩種方式，把外部資料收進系統。
情境

各縣市每月回報統計 Excel，格式不一，需自動彙入同一資料庫。

實作 
# 批次汲取：每月 5 日排程執行
for f in 收件匣附件("*.xlsx"):
    df = pd.read_excel(f)
    df["來源縣市"] = 解析檔名(f)
    寫入資料庫(df, table="raw_monthly")

重點：先原封不動存入「原始層」（raw），再另做清洗層——保留原始資料，出錯時才能追溯重跑。

資料轉換 Transformation範例教學
清洗、標準化與加值，讓資料可分析、可比對。
情境

各單位日期寫法不一（113/5/1、2024-05-01、5月1日），縣市名稱有簡稱與全稱混用。

實作 
df["日期"] = 統一為西元(df["日期"])   # 民國→西元
df["縣市"] = df["縣市"].map(縣市對照表) # 北市→臺北市
df = df.drop_duplicates(subset=["案件編號"])

重點：轉換規則寫成對照表與函式集中管理，不要散落各處；每次清洗記錄「改了幾筆、為何改」。

向量資料庫 Vector Databases範例教學
以語意相似度檢索，找「意思相近」而非「字面相同」。
情境

查「救護車收費」相關規定，傳統關鍵字搜尋會漏掉寫成「緊急救護費用」的條文。

實作（概念流程） 
法規逐條 → 嵌入模型（embedding）→ 向量存入 DB
查詢句 → 同一嵌入模型 → 取相似度 Top 5 條文

重點：文件切塊（chunking）大小是關鍵——法規以「條」為單位切、報告以「段」切，檢索精度差很多。

檢索增強生成 Retrieval-Augmented Generation, RAG範例教學
先檢索相關文件，再讓 LLM 依據文件作答，有憑有據。
情境

希望 AI 回答法規問題時「引用條文」而不是憑印象作答。

實作（RAG 三步） 
1. 檢索：向量庫取回最相關 5 條條文
2. 組裝：條文 + 使用者問題 一併放入提示
3. 生成：要求「僅依所附條文作答並註明條號，
   查無依據時明確回答『所附資料未規定』」

重點：最後一句「查無依據就說沒有」是 RAG 抑制幻覺（hallucination）的核心指令，務必寫入。

L5

可觀測性 （LLMOps）

Observability

看得見才管得住：記錄每次呼叫、管理每版提示、自動評分輸出、失敗時有備援。

日誌與追蹤 Logging & Tracing範例教學
記錄每次提示、回應、延遲與錯誤。
情境

某天摘要品質突然變差，需要回查是哪一版提示、哪個模型、哪筆輸入造成。

實作（記錄欄位） 
{ trace_id, 時間, 模型, 提示版本,
  輸入tokens, 輸出tokens, 延遲ms,
  狀態: 成功/失敗, 錯誤訊息 }

重點：trace_id 貫穿整條流程（觸發→檢索→生成→輸出），跨節點查問題時才串得起來。

提示版本管理 Prompt Versioning範例教學
提示詞如同程式碼，需版本化管理與回滾能力。
情境

提示改了三次後效果變差，卻想不起前一版怎麼寫。

實作（Git 管理） 
prompts/
  摘要_v1.md   # 每版獨立檔案
  摘要_v2.md   # commit 訊息記錄「為何改」
# 系統呼叫時載入指定版本，日誌記下版本號

重點：改提示前先留存舊版與測試案例，改完跑同一批案例比較——「憑感覺改提示」是品質不穩的最大來源。

評估管線 Evaluation Pipelines範例教學
用固定測試集自動評分輸出品質。
情境

公文分類提示每次修改後，需確認 50 筆標準案例的準確率沒有退步。

實作 
for 案例 in 測試集(50筆):
    結果 = 分類(案例.全文, 提示版本)
    正確 += (結果 == 案例.標準答案)
準確率 = 正確 / 50   # 低於前版即擋下上線

重點：測試集要含刁鑽案例（模稜兩可、格式異常）；主觀品質可再用另一個 LLM 當評審（LLM-as-judge）。

備援模型 Fallback Models範例教學
主模型故障或逾時，自動切換備援以維持服務。
情境

每日 07:00 自動產生晨報，主模型服務中斷不能讓晨報開天窗。

實作 
try: 回應 = 呼叫(主模型, timeout=30)
except (逾時, 服務錯誤):
    回應 = 呼叫(備援模型)
    日誌.warning("已切換備援")

重點：備援切換必須記錄並告警，否則主模型壞了三天都沒人發現；備援輸出格式需與主模型相容。

L6

擴展性

Scalability

量大時系統不塌：能平行就平行、忙不過來就排隊、依負載伸縮、依任務挑模型。

平行執行 Parallel Execution範例教學
彼此獨立的任務同時執行，縮短總時程。
情境

100 份文件逐一摘要需 50 分鐘；文件彼此獨立，可平行處理。

實作（Python） 
import asyncio
tasks = [摘要(doc) for doc in 文件清單]
結果 = await asyncio.gather(*tasks)  # 併發上限另設

重點：平行度受 API 速率限制（rate limit）約束，需搭配「併發上限＋排隊」；任務間有相依關係就不能平行。

工作佇列 Worker Queues範例教學
任務先入佇列，由多個工作者依序領取處理。
情境

上班時間大量請求湧入，直接處理會逾時；改為「先收單、後處理」。

實作（概念） 
請求 → 入列（queue）→ 立即回覆「已受理，編號 #123」
Worker ×3 ← 從佇列領件 → 處理完成 → 通知結果

重點：佇列把「尖峰」削成「平均」；務必設計失敗重入列與死信佇列（dead-letter queue），失敗任務才不會蒸發。

自動擴展 Auto-Scaling範例教學
依負載動態增減運算資源。
情境

平日一台主機足夠，月底報表期負載暴增五倍。

實作（雲端設定概念） 
規則：CPU > 70% 持續 5 分鐘 → 加開 1 台（上限 5）
      CPU < 30% 持續 10 分鐘 → 縮回 1 台（下限 1）

重點：擴展的前提是服務「無狀態」（stateless）——狀態放資料庫或佇列，任何一台機器都能接手任何請求。

模型路由 Model Routing範例教學
依任務難度選用不同等級模型，兼顧成本與品質。
情境

所有任務都用旗艦模型，成本高且多數任務用不到；建立分級選用規則。

實作（路由表） 
分類、貼標、格式轉換     → 輕量模型（快、便宜）
摘要、翻譯、一般文件草擬 → 中階模型
政策分析、長文推理、審查 → 旗艦模型

重點：路由規則來自評估資料——先用旗艦模型建立「標準答案」，再測輕量模型達標的任務類型，達標者降級。

L7

安全與治理

Security & Governance

身分驗證、最小權限、個資保護、輸出把關——公部門導入 AI 的先決條件。

OAuth 與 API 金鑰 OAuth + API Keys範例教學
安全的存取控制：識別「誰」在呼叫服務。
情境

自動化流程需存取雲端硬碟與信箱，不能把帳號密碼寫死在程式裡。

實作（原則） 
API 金鑰 → 存於環境變數/密鑰管理服務，絕不寫入程式碼或版控
OAuth   → 授權特定範圍（scope），如「唯讀信件」
         而非整個帳號

重點：金鑰定期輪換、一服務一金鑰；金鑰若曾提交進 Git，即視同外洩，立即作廢重發。

角色權限控管 Role-Based Access Control, RBAC範例教學
最小權限原則：每個角色只拿得到必要的權限。
情境

摘要機器人只需要「讀」文件，卻拿到了整個雲端硬碟的「讀寫刪」權限。

實作（權限表） 
摘要服務   → 指定資料夾：唯讀
產文服務   → 輸出資料夾：讀寫；其餘：無
管理者     → 全域：讀寫（需雙因子驗證）

重點：權限依「服務」而非「人」授予；每季盤點一次，用不到的權限立即收回。

資料隱私 Data Privacy範例教學
加密與個資遮罩，個資不進模型。
情境

要用 AI 分析案件紀錄，但紀錄含姓名、身分證號等個人資料（Personally Identifiable Information, PII）。

實作（送模型前遮罩） 
原文：王〇〇，A123456789，主訴胸痛
遮罩：[姓名]，[身分證號]，主訴胸痛
# 遮罩對照表僅存於內部，分析結果回填時還原

重點：遮罩要在資料離開內部環境之前完成；統計分析多數情境根本不需要個資欄位，能刪就刪。

AI 護欄 AI Guardrails範例教學
對模型輸出做安全與合規強制檢核。
情境

對外回覆的草稿由 AI 產生，需防止出現未經核定的政策承諾或錯誤法條。

實作（輸出檢核層） 
輸出 → 規則檢核：禁用語清單、法條號格式驗證
     → 引用檢核：引述條文需存在於法規庫
     → 未通過 → 退回重生成或轉人工

重點：護欄放在「輸出後、送出前」，與提示內的要求互為雙保險——提示會被忽略，檢核程式不會。

L8

效能與成本

Performance & Cost

失敗要能重試、重複要能快取、語境要能壓縮、費用要能追蹤到每條流程。

重試邏輯 Retry Logic範例教學
優雅處理暫時性失敗，不因一次錯誤中斷全流程。
情境

API 偶發逾時或限流（429），立即重打只會加劇壅塞。

實作（指數退避） 
for i in range(4):
    try: return 呼叫API()
    except 暫時性錯誤:
        sleep(2**i + 隨機抖動)  # 1s→2s→4s→8s
raise 最終失敗  # 進死信佇列並告警

重點：只重試暫時性錯誤（逾時、429、5xx）；參數錯誤（4xx）重試一百次也不會好，直接失敗告警。

批次與快取 Batching & Caching範例教學
合併請求、重用結果，直接降低 API 成本。
情境

同一份法規說明每天被詢問數十次，每次都重新生成回答。

實作 
# 快取：相同輸入直接回存檔結果
key = hash(提示 + 輸入)
if key in 快取: return 快取[key]
# 批次：非即時任務集中夜間以批次 API 處理，單價常有折扣

重點：快取需設有效期限並在來源更新時失效；「即時性不重要」的任務改批次，是最容易省下的成本。

Token 最佳化 Token Optimization範例教學
壓縮語境（context），只給模型必要的資訊。
情境

每次都把 200 頁手冊全文塞進提示，費用高且模型抓不到重點。

實作（三招） 
1. 檢索取代全文：只送最相關段落（RAG）
2. 滾動摘要：長對話定期壓縮成摘要再續談
3. 精簡提示：範例留 2–3 個代表性案例即可

重點：語境不是越多越好——無關內容會稀釋注意力；「相關且精簡」同時省錢又提升品質。

成本監控 Cost Monitoring範例教學
逐工作流追蹤用量，費用可歸戶、可預警。
情境

月底帳單暴增，卻不知道是哪條流程吃掉預算。

實作 
# 每次呼叫記錄
{ 工作流: "每日晨報", 模型, 輸入tokens, 輸出tokens, 費用 }
# 週報彙總：各工作流費用排行 + 月預算 80% 預警

重點：費用要能歸戶到工作流層級才有管理意義；設「單次呼叫 token 上限」防止異常輸入造成天價帳單。

L9

AI 控制與對齊

AI Control & Alignment

讓 AI 只做被允許的事：邊界由政策定義、可靠度有指標、關鍵動作人工把關、錯誤回饋持續改進。

政策引擎 Policy Engine範例教學
以明文規則定義 AI 的行為邊界。
情境

AI 助理可以「草擬」文件，但不得「發送」；可以讀資料，但不得刪除。

實作（政策清單） 
允許：讀取指定資料夾、產生草稿、建立行事曆事件
禁止：對外發送郵件、刪除檔案、修改正式檔
條件：涉金額之文件 → 一律轉人工核可

重點：政策寫成機器可判讀的清單並由程式強制執行，而非只寫在提示裡「拜託模型遵守」。

信心評分 Confidence Scoring範例教學
量化每次輸出的可靠程度，作為分流依據。
情境

分類任務需要知道模型「多有把握」，才能決定要不要人工複核。

實作（自評 + 校驗） 
提示要求輸出：{ "類別": ..., "信心": 0–1, "理由": ... }
定期抽驗：比對「自評信心」與「實際正確率」
偏差過大 → 調整分流門檻

重點：模型自評信心常常過度自信，必須用抽驗資料校準門檻，不能直接採信。

人工核可關卡 Human Approval Gates範例教學
關鍵動作執行前，強制經人工確認。
情境

自動化流程可產生對外函稿，但「送出」這個動作影響重大，不可全自動。

實作 
草稿完成 → 推播審核連結給承辦人
承辦人檢視 → 按「核可」→ 系統始執行發送
逾 24 小時未核可 → 提醒；絕不逾時自動放行

重點：核可關卡設在不可逆動作之前（發送、付款、刪除、對外公開）；「逾時自動通過」是最常見的設計錯誤。

回饋迴圈 Feedback Loops範例教學
收集修正紀錄，讓系統持續改進。
情境

承辦人常修改 AI 草稿的同一類問題（語氣、格式），但系統從未從中學習。

實作 
1. 保存「AI 草稿 vs 人工定稿」差異
2. 每月彙整高頻修正模式
3. 更新提示範例或風格規範 → 跑評估集驗證
4. 新版上線 → 觀察修正率是否下降

重點：回饋要回到提示與評估集才算閉環；只收集不利用的回饋等於沒有回饋。
