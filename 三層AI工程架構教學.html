AI Engineering · Three Layers

提示工程 × 情境工程 × 框架工程
三層 AI 工程架構完整教學

同一顆大型語言模型（Large Language Model, LLM），可以只回一句話，也可以自動跑完一整條文件產製管線。差別不在模型本身，而在你於哪一層做工程：訊息層、記憶層、機器層。三層是嵌套關係，不是取代關係。

第三層｜框架工程 Harness Engineering ——「機器」

設計整個自動化系統：蒐集 → 執行 → 驗證的迴圈、子代理分工、失敗重試。

第二層｜情境工程 Context Engineering ——「記憶」

管理有限的情境視窗：決定哪些資料留下、壓縮、丟棄，逐步維護模型「看得到什麼」。

第一層｜提示工程 Prompt Engineering ——「訊息」

組裝單一次輸入：角色、背景、指令、範例、輸出格式。

框架包含情境，情境包含提示——外層做得好，內層才有發揮空間。

面向提示工程情境工程框架工程
比喻訊息（The Message）記憶（The Memory）機器（The Machine）
工作單位一次輸入（one input）每一步「留在視窗內的內容」整個任務管線（gather → act → verify）
核心問題這次要怎麼「說」？模型此刻該「看到」什麼？系統要怎麼「自己跑完並驗證」？
核心操作組裝：角色＋背景＋指令＋範例＋格式策展：挑選（select）、壓縮（compress）、丟棄（drop）編排：工具呼叫、子代理、驗證器、重試
優化方式調整最弱的那個提示元件調整視窗預算分配調整迴圈與驗收標準
失敗徵兆答非所問、格式錯誤、風格不對長對話後遺忘、幻覺、抓錯重點單步都對、整體流程卻走偏或無法收斂
典型工具提示模板、少樣本範例（few-shot examples）檢索增強生成（Retrieval-Augmented Generation, RAG）、摘要壓縮、記憶系統代理框架（agent framework）、Claude Skills、n8n、驗證腳本
判斷順序建議：由內而外。先確認提示寫對（同樣輸入單獨測試是否正確）→ 再檢查情境（模型當下視窗內有沒有它需要的資料）→ 最後才動框架（流程設計與驗證機制）。
Layer 1

提示工程｜組裝一則精準的訊息

提示工程（Prompt Engineering）的工作單位是「一次輸入」。目標：把角色、背景、指令、範例與輸出格式組裝成一則完整訊息，讓模型在單次推論中產出正確結果。

運作流程

① 組裝 Compose五大元件 → 完整提示
→
② 送出 Send一次輸入
→
③ 生成 GenerateLLM 推論產出
→
④ 精修 Refine調整最弱元件，重跑

五大提示元件

元件功能公務情境示例
角色 Role設定專業視角與行文立場「你是中央機關承辦人，熟悉行政程序與公文格式」
背景 Context提供任務所需的文件與事實貼上會議紀錄、法規條文、前次函稿
指令 Instructions明確定義要做什麼、步驟為何「依三段式架構撰寫簽稿：主旨、說明、擬辦」
範例 Examples用少樣本範例示範期望的輸入→輸出附一份過去核定的同類簽稿當寫作樣板
格式 Format指定輸出結構（表格、JSON、字數）「說明分點條列，每點不超過 60 字」

實作範例：撰寫研討會簽稿

✗ 弱提示（缺角色、背景、格式）

模型只能靠猜，產出格式與用語通常不符機關慣例。

幫我寫一份辦理國際研討會的簽。
✓ 強提示（五元件齊備）

角色、背景、指令、範例、格式各就各位，可一次到位。

【角色】你是中央機關承辦人，熟悉三段式簽稿。 【背景】本科擬於 115 年 9 月辦理國際研討會， 已邀 5 位國外講者，經費 120 萬元，由年度預算支應。 【指令】撰寫陳核簽稿，重點：辦理依據、 講者與議程規劃、經費來源、行政分工。 【範例】（附去年核定簽稿一份，比照其語氣） 【格式】主旨一句話；說明分點；擬辦兩案並敘明建議。
精修原則：結果不理想時，不要整段重寫，而是找出「最弱的元件」單點調整——格式錯就補格式規範、語氣錯就換範例、內容錯就補背景。一次改一項，才能定位真正的問題來源。
Layer 2

情境工程｜經營模型的工作記憶

情境工程（Context Engineering）的工作單位是「每一步留在視窗內的內容」。情境視窗（context window）是有限預算：塞得越滿，模型注意力越稀釋。策展人（curator）的任務是持續決定挑選、壓縮、丟棄。

運作流程

① 蒐集 Gather六大來源匯入
→
② 策展 Curate挑選／壓縮／丟棄
→
③ 餵入 Feed放進有限視窗
→
④ 更新 Update新產出成為下一步的情境

六大情境來源

使用者查詢 User query

本次任務的核心問題，永遠優先保留。

系統提示 System prompt

常駐的角色設定與行為規範（如 Skill 內的規則）。

檢索文件 Retrieved docs

從知識庫或雲端硬碟撈出的相關文件段落。

工具輸出 Tool outputs

搜尋結果、程式執行結果、API 回傳資料。

記憶 Memory

跨對話累積的長期偏好與專案背景。

先前輪次 Prior turns

本對話的歷史訊息——最容易膨脹的來源。

策展三操作

操作做法公務情境示例
挑選 Select只放與本步驟直接相關的內容審規格書時只放本案 RFP 第三章，而非整包 200 頁招標文件
壓縮 Compress長文件先摘要成要點再放入三場會議紀錄先各壓成 10 條決議，再一起比對
丟棄 Drop移除已完成階段的過程性內容初稿討論定案後，開新對話只帶「定稿＋修改原則」

實作範例：長對話處理採購案

✗ 無策展

同一對話從需求訪談聊到驗收，貼進 5 份完整文件。50 輪之後模型開始混用不同版本的規格數字——不是模型變笨，是視窗裡塞了互相矛盾的舊資料。

✓ 有策展

每完成一階段就請模型輸出「階段摘要」，開新對話時只帶三樣東西：

# 新對話的起手情境 1. 本案基本資料（案名、預算、期程）— 200 字 2. 上一階段定案摘要 — 10 條要點 3. 本階段唯一任務文件（規格書 v3 全文）
核心心法：情境視窗是「工作桌面」不是「檔案櫃」。桌上只放正在用的文件；其餘進檔案櫃（知識庫、專案文件），需要時再檢索。判斷標準：這段內容若刪掉，模型下一步會做錯嗎？不會，就丟。
Layer 3

框架工程｜打造會自我驗證的機器

框架工程（Harness Engineering）的工作單位是「整條任務管線」。它把前兩層包進一個可重複執行的迴圈：蒐集（Gather）→ 執行（Act）→ 驗證（Verify），驗證未通過就帶著更新後的情境重跑，直到產出通過驗收才交付。

運作流程

① 蒐集 Gather情境工程區：策展 → 有限視窗
→
② 執行 Act提示工程區：組裝提示 → 呼叫工具／子代理
→
③ 驗證 Verify測試腳本／LLM 評審
→
通過 → 交付未通過 → 帶新情境重跑

四個關鍵構件

工具輸出 Tool outputs

計算、檢索、檔案處理交給確定性工具，不讓模型「用想的」——數字用程式算，法條用檢索查。

子代理 Sub-agent specialists

把大任務拆給多個專職代理：一個起草、一個核對法規、一個檢查格式，各自持有乾淨的小情境。

驗證器 Verifier

可執行的驗收標準：格式檢核腳本、必要欄位清單，或由 LLM 擔任評審（LLM-as-judge）逐項評分。

重試迴圈 Retry loop

驗證失敗不是終點：把失敗原因寫回情境，重新走 Gather → Act → Verify，直到收斂。

實作範例：公文自動審查管線

以「文件多角色審查」為例——這正是把單次提示升級為框架的典型場景：

# 管線設計（可用 Claude Skill、代理框架或 n8n 實作） Gather 載入待審文件 + 審查基準（法規要點、格式規範） → 策展：只放本件全文與對應規範，不放歷史案件 Act 子代理 A（法制視角）：檢核引據條文是否正確 子代理 B（主計視角）：檢核經費表述與科目 子代理 C（幕僚視角）：檢核三段式架構與用語 → 各自輸出結構化審查意見（JSON） Verify 驗證器逐項比對： - 必要欄位是否齊備（主旨／說明／擬辦） - 三份意見是否互相矛盾 → 矛盾則標記人工裁決 - 通過 → 彙整為單一審查報告交付 - 未通過 → 把缺漏清單寫回情境，重跑 Act
✗ 只靠一次提示

「幫我審這份公文」——單一視角、無驗收標準，漏了也不知道漏，每次品質浮動。

✓ 框架化

多角色分工＋明確驗收清單＋失敗重跑。品質由「流程」保證，而非單次運氣；且可重複用於每一份新文件。

核心心法：框架工程的價值在「驗證器」。沒有可執行的驗收標準，迴圈就無從收斂——先寫得出「怎樣算通過」，才值得蓋機器。

實務進階路徑：何時該升級到下一層

不是每個任務都需要三層。以任務特性判斷停在哪一層，避免過度工程。

任務特性停在哪一層典型任務
一次性、資料可全放進單一訊息提示工程改寫一段文字、單份簽稿起草、翻譯、單表摘要
多輪、多文件、跨階段，資料超出單次可貼範圍＋情境工程採購案全程協作、法規研修比對、長期專案追蹤
重複性高、可定義驗收標準、想無人化執行＋框架工程每日資料彙整自動化、批次文件審查、例行報表產製

三步升級練習

STEP 1把慣用任務寫成提示模板

挑一項每週重複的文書任務，依五元件寫成固定模板，連續使用兩週並每次只修一個元件。

STEP 2為長專案建立情境紀律

訂定「階段摘要」習慣：每完成一階段輸出定案摘要，開新對話只帶摘要＋當前文件。

STEP 3為一項例行任務蓋框架

先寫驗收清單，再設計 Gather → Act → Verify 流程，最後才選工具（Skill／n8n／腳本）實作。

常見誤區

誤區問題修正
用提示解決情境問題長對話出錯就一直加指令「請記得前面說的」，越加越亂問題在視窗不在措辭——做摘要、開新對話、重新策展
視窗當檔案櫃一開始就貼滿所有可能用到的文件，注意力被稀釋採「按需檢索」：先給索引，需要哪段再取哪段
沒有驗證器就蓋框架自動化流程跑得動，但產出品質無從把關先定義可檢核的驗收標準，再談自動化
一個代理包山包海單一代理背負超長系統提示，角色互相干擾拆成子代理，各持小而乾淨的情境
過度工程一次性任務也蓋管線，維護成本高於效益用「重複頻率 × 驗收可定義度」判斷是否值得框架化
